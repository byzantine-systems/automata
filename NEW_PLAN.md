## Status

**Phase A is done and merged** (PR #22, `cf28225`). Every later phase builds on what it left in place:

- No `try/with` in runners: `ResiliencePipeline.executeOutcome` settles each attempt, `Db.classify` maps it to `Cancelled | Unavailable | Violated | Unexpected`. Public `StoreError.Unexpected of exn`.

Carried over from Phase A, still open:

- actionlint rejects `pull_requests` in `.github/workflows/dependabot-addons.yml`.
- `try/with` outside the runners: the codecs, the SQLite migrator, `decodePath`, Core `Boundary`, the Runtime dispatchers, and the DI hosted services. Phase B narrows the codec ones; the rest are legitimate boundaries.

### What changed from the previous plan

1. **The CE work continues as Phase B**, rewritten around a **store algebra**. Phase A built the effect; Phase B gives both SQL providers one semantic instruction set, one `store { }` program per concern and one interpreter per provider, so the choreography that today exists twice (PostgreSQL and SQLite, already drifting) is written once.
2. **New phases A2, A3 and A4, the core algebra track.** The chart and rule vocabulary gets an explicit law portfolio and generated tests (A2), a two-tier condition DSL with a canonical syntax fingerprint (A3), and a public chart-equivalence API (A4). The A track touches only Core, so it runs before and alongside Phase B.
3. **New Phase C, correctness fixes.** The review found real bugs: a maintenance wedge, an ordering race, and poison-row wedges. They get fixed before any structural change. **C0 also creates a provider-agnostic conformance suite**, so each fix is proven once against every store.
4. **New Phase D, configurable schema.** The default stays `fsm`.
5. **New Phase E, bitemporal opt-in.** The timeline moves to a sibling schema `<schema>_temporal`, installed only on request. The core schema keeps a plain snapshot table. Corrections ship with the temporal module. The infrastructure they need becomes public interfaces, so an application can implement corrections over the core store itself.
6. **Phase B gains B10 and B11.** B10 replaces the runtime's recursive `task` loops, which leak per iteration and can overflow the stack. B11 brings the library in line with Microsoft's TAP guidance, translated to F#: a functional core with a thin `Task` shell.
7. **The in-memory store is withdrawn from the plan.** The earlier draft had it as Phase F. Its two load-bearing roles are covered better elsewhere: the law-testing and reference-implementation role by the store algebra's recording interpreter (Phase B), and the corrections-evidence role by a test-only `IPriorState` and `ICorrectionCommitter` (Phase E). Its own section is gone; E44 and E49 were real bugs independent of it and are re-homed.
8. **The old Phase B (JSON reduction) is now Phase G**, adjusted for the split. The old Phase C (DB-enforced lifecycle) is now Phase H.
9. **"No public API change" is lifted.** Automata is unreleased. Every public change is listed in its phase and recorded in `docs/public-api.md`. There is still no version bump, tag or CHANGELOG.

## Phase A2: the core algebra: laws, generators, observations (no schema change, no public change)

Everything in A2 works against today's closure encoding. That is deliberate: the laws are written and tested before A3 changes the representation they constrain, which is the only order in which a representation swap is safe.

### A2.1 The law portfolio

Each law names its **observation** (the public function the equality is claimed under) and its **scope** (which terms it covers). Laws are listed here as the spec; A2 turns each into a named FsCheck property.

Rule laws (observation `Rule.invoke`, syntax `Rule.kind`):

| Law | Statement |
|---|---|
| Guard transparency | When the guard predicate holds, `invoke (guarded p reason r) = invoke r` on the same pair. When it does not, `invoke (guarded p reason r) = GuardFailed reason`, independent of the wrapped rule. |
| Constructor refinement | For each combinator, the verdict is a total function of its predicate and transform: `transition` answers `NoMatch` exactly when the predicate does not hold, `attempt` maps `Error` to `Rejected`, `internalOn` never changes the state, `goto` echoes its target. |
| Kind injectivity | `kind` names the combinator that built the rule; `kind (goto p t tr) = Goto t` and `kind (guarded p reason r) = Guarded (reason, kind r)`. |
| Target projection | `target (goto _ t _) = Some t` and `target (guarded _ _ r) = target r`; the other combinators answer `None`. |
| Retarget homomorphism | `invoke (retarget f r) s e` equals `invoke r s e` with `Goto` targets mapped through `f` and every other verdict untouched, both through guards. |

Chart laws (observation `Chart.resolve`):

| Law | Statement |
|---|---|
| Internal identity | An `internalOn` match resolves `Ok` with `Exited = []`, `Entered = []` and `Next` the same state. |
| Chain locality | Resolution consults only nodes on `Hierarchy.chain` of the classified leaf; an event handled by an off-chain node is `Unhandled`. |
| First match wins | Within a node, the first rule whose verdict is not `NoMatch` decides; later rules are unreachable for that pair. |
| LCA path law | `Exited` is exactly the prefix of `chain leaf` below the least common ancestor of leaf and target; `Entered` is the outermost-first suffix of `chain target`. |
| Self-transition | When handler and leaf differ and the target is the leaf itself, `Exited` is the path leaf to handler and `Entered` its reverse. |
| Goto descent | A `goto` resolves at the target's initial-child leaf, and `Classify nextState` must equal that leaf or the answer is `TargetMismatch`. |
| Actions order | `Actions = exit actions ▸ rule actions ▸ entry actions`, concatenated in execution order. |
| Anchors | A chart with exactly one matching rule resolves `Ok` and names the handler (rules out the always-`Unhandled` degenerate model); a terminal leaf is `Unhandled` by construction. |

Hierarchy laws (observation the module functions, over generated parent functions): `leastCommonAncestor a b = leastCommonAncestor b a`; `leastCommonAncestor a a = a`; `chain` starts at the node, ends at the root, is strictly parent-linked and duplicate-free; `pathUpTo` is a prefix of `chain`.

Fragment laws (observation the built chart, plus `Chart.fingerprint`):

| Law | Statement |
|---|---|
| Splice monoid | Part splicing is associative with `Zero`, and rule declaration order survives splicing, because order is observable (first match wins). |
| Prefix compositionality | `prefix "a" (prefix "b" d) = prefix "a.b" d`, and `prefix` distributes over child splicing. |
| Classifier boundary | `prefix` cannot rename classifier outputs. This is a stated law boundary, not a silent gap: the classifier is the host's own code and the failure is typed (`UnknownState`), never a wrong resolution. |
| Fingerprint stability | Renaming sibling declaration order leaves the fingerprint unchanged; reordering rules changes it. |

### A2.2 Generators

The generators in `ChartPropertyTests.fs` grow into the portfolio's engine, under the rules that make generated evidence trustworthy:

- Terms are built **through the public constructors only** (the `statechart` CE, the `Rule` and `Fragment` combinators). Nothing constructs a `Node` or a `Rule` record directly, so unreachable states are not generated.
- Recursion is sized, every constructor of `Rule`, `NodePart` and `Condition` (once A3 adds it) has a route, and the frequencies are biased so compound shapes occur.
- Coverage is asserted, not just reported: a property whose generator cannot reach a constructor family is a generator defect, and the suite says so.

### Phase A2 verification

- Every law above is a named property; the suite fails if one is missing.
- `dotnet build bs-automata.slnx`, `make test-unit`, `make fmt`.
- No change under `src/` other than test-only additions.

## Phase A3: the two-tier condition DSL, canonical syntax fingerprint (no schema change; public rule surface)

### A3.1 The condition language

`Rule` starts with a coarse `Kind` projection and an opaque `Invoke` closure. A3 adds normalized condition and rule syntax while keeping predicate delegates executable. The syntax is inspectable and hashable; delegate behavior remains opaque.

```fsharp
type ConditionSyntax =
    | Always
    | Never
    | AllOf of ConditionSyntax list
    | AnyOf of ConditionSyntax list
    | Not of ConditionSyntax
    | EventIs of name: string
    | StateIs of name: string
    | Both of name: string
    | Custom of name: string

type Condition<'State, 'Event> = private Condition of ConditionSyntax * ('State -> 'Event -> bool)
```

- Every predicate carries a stable caller-supplied name. The fingerprint records syntax and names, never delegate behavior; reusing one name for different behavior is a broken caller contract.
- `matches` is the observation, and it is a **homomorphism** onto the boolean algebra: `matches (AllOf [a; b]) s e = matches a s e && matches b s e`, `matches Always = true`, `matches Never = false`, `Not ∘ Not = id`, and De Morgan holds between `AllOf`/`AnyOf`/`Not`. `AllOf`/`Always` and `AnyOf`/`Never` are commutative monoids. These are laws, with properties.
- Smart constructors normalize empty and singleton groups, identities, annihilators, nesting, ordering, constants, and double negation. Callers cannot construct noncanonical syntax.
- A finite toy signature enumerates terms and truth tables. Accepted equalities become named properties; a self-check rejects syntax collisions with different observations.

### A3.2 Rules over the DSL

- `Rule.transitionWhen`, `attemptWhen`, `gotoWhen`, `internalWhen`, and `guardedWhen` take conditions. Existing closure functions stay source-compatible and use fixed legacy `Custom` syntax.
- `RuleSyntax` combines the combinator, condition syntax, target, and guards. `RuleKind` stays as a compatibility projection.
- `Fragment.prefix` and `Rule.retarget` become syntax rewrites; the A2 homomorphism laws now hold structurally, which is worth a comment on each.
- The fingerprint scheme bumps `automata.chart.fingerprint/1` to `/2`: normalized rule and condition syntax is hashed. It is exact for declared syntax, not resolution behavior; transforms, actions, classifiers, and predicate delegates remain opaque.
- `docs/public-api.md` records the change. No version bump.

### Phase A3 verification

- The full A2 portfolio passes unchanged: the laws did not move when the representation did, which is the point.
- Fingerprint properties: equal normalized syntax has one fingerprint; condition categories and names are structural; `Custom` changes the fingerprint only through its name.
- Normalization laws; mini-QuickSpec run reviewed and its accepted laws folded into the suite.
- `dotnet build bs-automata.slnx`, `make test-unit`, `make fmt`.

## Phase A4: public chart equivalence (no schema change; public, additive)

The trace observation A2 used internally becomes public, with its honesty stated on the type:

```fsharp
module ChartEquivalence =
    /// One observable step: what the outside can see of a resolution.
    type Step<'A> = { Leaf: StateId; Terminal: bool; Actions: 'A list }
    /// The successful prefix and first failure of a trace.
    type TraceFailure<'A,'Err> = { Steps: Step<'A> list; Error: TransitionError<'Err> }
    /// Runs an event sequence, stopping at the first typed resolution failure.
    val trace : Chart<'S,'E,'A,'Err> -> 'S -> 'E list -> Result<Step<'A> list, TraceFailure<'A,'Err>>
    /// Trace equality over a caller-supplied suite of event sequences. Samples, never proves.
    val equivalentOn :
        ('A -> 'A -> bool) ->
        (TransitionError<'Err> -> TransitionError<'Err> -> bool) ->
        'E list list ->
        Chart<'S,'E,'A,'Err> * 'S ->
        Chart<'S,'E,'A,'Err> * 'S -> bool
    /// Exact equality of canonical declared syntax; not behavioral equivalence.
    val declaredEquivalent : Chart<'S,'E,'A,'Err> -> Chart<'S,'E,'A,'Err> -> bool
```

- The observation is deliberately **not** `'State` equality: two states that classify to the same leaf are observationally equal, so the trace compares leaves, terminal flags and typed actions. Representation does not leak.
- A trace returns its successful prefix with the first typed failure. `equivalentOn` takes action and error equality explicitly, avoiding equality constraints on domain types.
- `equivalentOn` documents that a finite suite is evidence, not proof. `declaredEquivalent` compares canonical syntax directly rather than relying on hash equality; predicate delegates and transforms remain outside it.
- Minimization of charts is **considered and not adopted**: the trace algebra makes it possible later, and nothing today needs it.
- `docs/public-api.md` records the addition.

### Phase A4 verification

- Properties: reordered siblings and normalized condition spellings are declaration-equivalent; generated traces exercise behavioral agreement separately.
- Tests pin the distinction between syntax equality and sampled behavior.

## Phase B: the store algebra, types, runtime loops, TAP (no schema change)

A store method should read as what it decides, and nothing stringly-typed should cross an internal boundary. Both providers answer through one instruction algebra, so the choreography is written once and each provider supplies statements and session mechanics. Tests stay unchanged except where a signature tightens.

### B0. The store algebra: one program per concern, one interpreter per provider

Today every store concern exists twice. `PostgresCommandInbox.fs` and `SqliteCommandInbox.fs` spell the same submit/claim choreography over the same decisions with different statements, and the review has already caught them drifting (E29). The remedy is not a third copy with a test suite; it is to write the choreography **once** as a program in a small instruction algebra, and make each provider an interpreter of it.

```fsharp
/// The instruction set: the store algebra's signature, at statement granularity.
type StoreInstruction<'Next> =
    | Execute      of key: StatementKey * kind: WriteKind * ps: Params * next: (int -> 'Next)
    | QueryOne     of key: StatementKey * ps: Params * read: Read<'Row> * next: ('Row -> 'Next)
    | TryQueryOne  of key: StatementKey * ps: Params * read: Read<'Row> * next: ('Row option -> 'Next)
    | QueryRows    of key: StatementKey * ps: Params * read: Read<'Row> * next: ('Row list -> 'Next)
    | WithEntityGate of entity: EntityKey * body: StoreProgram<'Next>
    | InSession    of SessionKind * body: StoreProgram<'Next>

and StoreProgram<'T> = Pure of 'T | Impure of StoreInstruction<StoreProgram<'T>>

type store = StoreBuilder()   // Bind/Return/Zero/Combine/Delay over StoreProgram
```

- **`StatementKey`** is the semantic key the providers already use (`Statement.load domain operation`, the D2 mechanism). The program names what it wants ("`command/finalize`"); the interpreter supplies the provider's text. SQL stays data.
- **`WithEntityGate`** is where the two providers genuinely differ, made explicit: PostgreSQL interprets it as the per-entity advisory-lock statement inside the routine call; SQLite interprets it as the `IMMEDIATE` write session itself, whose transaction is the gate. The instruction is the shared meaning, the realization is per provider.
- **`InSession`** owns connection and transaction shape: read sessions, write sessions. Nesting rules are instruction laws (below).
- **Interpreters** live in each provider: a `StatementKey → Statement` map over the existing `SqlResources`, session and gate realization, and the existing runners, resilience pipeline and `Op` underneath. `Op` survives, demoted one level: it is how an interpreter talks to a driver, no longer how store logic is composed.
- **Programs replace choreography files.** `CommandInboxProgram`, `ActionQueueProgram`, `ProcessorProgram`, `TemporalProgram` and so on are written once in `Storage` and become the only place a SQL sequence is decided. A provider package shrinks to: interpreter, statements, migrations, boot, and the provider-true extras (LISTEN/NOTIFY, pgmq). Where choreography genuinely differs by provider, provider fragments compose at the program level rather than forking the file.
- **This reverses Phase A's "OpBuilder stays minimal" conclusion, on purpose.** Phase A kept `Op` a closure because nothing then needed a second interpreter. The store algebra needs two things a closure cannot give: provider-generic programs (the closure fuses program with session mechanics) and a pure interpreter for law tests. The initial encoding costs an allocation per instruction, which is noise under database I/O; the benchmark still runs before any performance sentence, per the repo rule.
- **Migration order**, each step green before the next: `Sql.fs` primitives become instruction constructors; the interpreter lands per provider; then store by store, **CommandInbox first** (it is the most duplicated), then ActionQueue, CommandProcessorStore, Temporal/Supervision/Maintenance; last, the dead per-provider choreography is deleted.

### B0.1 Instruction and program laws

Three tiers, each with its own tests:

1. **Instruction laws** (against a **recording interpreter**: pure, returns scripted outcomes, records the instruction log):
   - `WithEntityGate` composes: gating twice for one entity within a program runs the body once, nested gates for different entities interleave legally;
   - session normal form: one write session per program, read sessions never nested inside a write session's gate;
   - `Execute` with `WriteKind.Discard` never binds the count, mirroring B1.
2. **Interpreter laws**: each provider's interpreter, driven through the real runners, passes the C0 conformance suite. This is where per-provider behaviour is pinned.
3. **Behaviour preservation**: each provider's existing suite passes unchanged after that store's migration. The recording interpreter inherits the reference-implementation role the withdrawn in-memory store was to play: program-level outcomes are tested purely, without a database.

### B1. `do!` works on statements: `WriteKind` instead of `Op.discard` (absorbed)
The old `Sql.execute : Statement -> Params -> Op<_, int>` split becomes a constructor argument: `Execute (key, Discard, ps, next)` drops the count by type, `Execute (key, Count, ps, next)` hands it to the continuation. A `Bind` overload that silently drops counts was rejected in the Phase A draft for the same reason it stays rejected: inference between `'T` and `int` is fragile, and a silently dropped count is a bug.

### B2. Row readers return `Result`, folded into the instruction (absorbed)
The `Read<'Reader, 'T>` type moves from a per-provider helper to the algebra:

```fsharp
type internal Read<'T> = NpgsqlDataReader -> Result<'T, StoreError>   // per provider, at the interpreter
```

`QueryOne`/`TryQueryOne`/`QueryRows` carry it, so decode-after-read is part of the query, not a follow-up step. The `typeName: string` argument goes: errors name the statement key (`command/finalize returned no row`), which is more useful and kills the 9 string literals. A reader that throws is a defect (`Unexpected`); a reader that recognises bad data answers `Error(Serialization …)`.

### B3. One spelling table per database enum, both directions derived from it
Status and outcome strings are mapped by hand in both directions, in several copies:
- `outcomeFromString` twice in PostgreSQL;
- `Resolution.status : string`;
- `toResult` matching `"ready" | "leased"` directly, although `CommandMapping.statusFromString` exists;
- registration and divergence strings.

Replace them all with:
```fsharp
type internal Spelling<'T when 'T: equality> = private { Name: string; Cases: ('T * string) list }
module internal Spelling =
    /// `spell` is an exhaustive match, so a new case is a compile error here.
    let create (name: string) (all: 'T list) (spell: 'T -> string) : Spelling<'T>
    let toDb   (s: Spelling<'T>) (value: 'T) : string
    let ofDb   (s: Spelling<'T>) (text: string) : Result<'T, StoreError>   // unknown text is Serialization
    let read   (s: Spelling<'T>) (column: string) : Read<_, 'T>
```
Instances:
- `CommandStatus`, `InstanceStatus`, `FinalizeOutcome` (tag only), `LeaseUpdateOutcome`;
- `Divergence`, `CommandKind` (tag), `ChartRegistration` (tag);
- `SupervisionAuditKind`, `SupervisionAuditStrategy`.

They live once in `Storage.Internal` and are shared by the SQL providers. A pure test asserts that `all` covers `FSharpType.GetUnionCases` for each instance, and that `ofDb (toDb x) = Ok x`.

`toResult` then parses `CommandStatus` first and matches the union exhaustively. An unknown status becomes one `Serialization` error at the parse, not a wildcard arm.

### B4. Applicative decoding replaces the first-error tuple matches (7 sites)
`toTransition` (a 7-tuple), `toRecord` (twice), `encodeDraft` (twice), `readMessage` and the supervision decoder all spell out `| Error e, _, _ … -> Error e` by hand. FsToolkit's `result { let! … and! … }` expresses the same thing: independent decodes, first error wins. This is the same semantics with no arms to keep in sync. `validation { }` (accumulating every error) is rejected: `StoreError.Serialization` carries one cause, and a row that fails twice is one defect.

### B5. Decoders never throw
Several decoders call throwing constructors while reading a row: `MachineId.create`, `StateId.create`, `SupervisorName.create`, `ChartVersion.create` (inside `ReplayMapping`), `JsonDocument.Parse` and `JsonNode.Parse` (`BeliefPayload.fs:27`). Inside an `Op`, a throw becomes `Unexpected` and loses the "bad data" meaning. Outside the runner (claim decoding, see C3) it escapes as an exception.
- Add `tryCreate : string -> Result<_, string>` wherever Core lacks it. This is **public, additive**.
- Decoders call `tryCreate` and map failures to `Serialization`.
- `Serialization.protect` (both SQL providers) keeps catching at the codec boundary, but with `when not (isFatal e)`, so `OutOfMemoryException` and `InsufficientExecutionStackException` propagate.

### B6. Internal ids are typed
Raw values cross internal boundaries today:
- `FinalizeTarget = { Machine: string; Entity: string; Holder: int64 }`;
- `commandId: int64` threaded through `append`, `recordError`, `close` and `resolve` in `SqliteCommandProcessorStore`;
- `entityId: string` passed through `findExisting` and `submit` in both inboxes.

Introduce `[<Struct>] type internal EntityKey = private EntityKey of string`, the *encoded* entity id. Then:
- `EntityIdEncode` produces an `EntityKey` at one place per store;
- `FinalizeTarget` becomes `{ Machine: MachineId; Entity: EntityKey; Holder: LeaseToken<CommandWork> }`;
- `CommandId` is passed, never `int64`.

`Param` gains no cases: conversion to `Param.Text` / `Param.Bigint` happens in one `Params` helper per id type.

### B7. Constrained arguments instead of request-time `invalidArg`
`Claim`, `ExtendLease`, `Abandon`, `Run`, `Schedule`, `listRecent` and `register` validate their arguments with `invalidArg` inside `Task`-returning members, each at every call. The checks also differ by provider: PostgreSQL `Abandon` does not check `reason`, while SQLite's does (`SqliteActionQueue.fs:141`).

Make invalid values unrepresentable instead (**public, breaking, unreleased**):
```fsharp
[<Struct>] type ClaimBatch     = private ClaimBatch of int          // 1 ..= 1000
[<Struct>] type LeaseDuration  = private LeaseDuration of TimeSpan  // > 0 and <= Int32.MaxValue ms
type Reason = private Reason of string                              // non-blank, trimmed
```
Each type has `tryCreate`/`create`. The interfaces take these types. The runtime builds them once from `MachineBuilder` configuration, so a misconfiguration fails at build time, not on the first poll. `Backoff.tryCreate` also rejects a ceiling above `Int32.MaxValue` ms, which fixes the overflow in E17.

This matters for Phase B0 as well: a provider's interpreter inherits the validation instead of re-implementing it, and the shared programs never see an unvalidated argument.

### B8. Small CE and interpreter fixes
- **The interpreter leaks the connection** when a session constructor throws, and `Listener.openDirect` leaks it when `OpenAsync` throws (E19). Hold the connection under `use` until ownership passes, or dispose in a `try/finally` that ownership transfer disarms. The program layer cannot fix this; the interpreter owns sessions.
- **Claim's corrections read joins the claim** (E32). Today `Claim` makes two runs, `runOnce` claim then `run` correction details. If the second run fails, the batch is leased and the call answers `Error`, so every entity in it stalls for the lease. Make `claim_commands` (and SQLite `claim.sql`) return the correction columns through a `LEFT JOIN`, so a claim is one statement. The shared `CommandInboxProgram` fixes this once for both providers.
- **`PostgresMachineStore.boot`** uses `taskResult`. Switch it to `backgroundTaskResult`, like the rest of the library.
- **`StoreBuilder` stays minimal.** Still absent: binding a raw `Task` (a program must not open a second session under the first), `and!` (one connection cannot run two commands at once), `TryWith` (exception translation belongs to the interpreter's single boundary), `Using`. Add `For` only when a program needs a per-element loop. The Phase A finding carries over: the absences are the design.
- **Two `<summary>` blocks collide** (E18):
  - In `Processing.fs`, the `CommandFailure` comment sits above `ReplayError`.
  - In `PostgresCommandProcessorStore.fs:48-59`, the store's summary is attached to `ReplayMapping`.
  - The XML doc generator keeps the wrong one. Fix both.

### B9. .NET compliance
- **Logging:** use `LoggerMessage.Define` cached delegates in `DependencyInjection/Logging.fs` and `Maintenance.fs`, in place of `LogX(eventId, format, box …)`. F# has no source generators, and `Define` is the allocation-free equivalent.
- **Data source ownership:** `PostgresContext.ofConnectionString` builds an `NpgsqlDataSource` that nobody owns. Remove it from the public surface and keep `PostgresContext.create dataSource policy sink`. Examples build the data source under `use`. A host registers it once, through DI.
- **Clocks:** `PostgresTemporalStore.ValidAt` reads `DateTimeOffset.UtcNow`. That changes in E (one clock, the database's); until then, use `TimeProvider`.
- **Cancellation:** `SqliteBoot.fs:141` calls `CloseAsync()` without the token. Both migrators stay synchronous, because DbUp is synchronous; document this rather than wrap it in `Task.Run`.

### B10. Runtime loops become `while` loops (E41)
The long-running loops are recursive `task`/`backgroundTask` functions using `return!`:
- `CommandProcessor.RunAsync.loop` (`CommandProcessor.fs:504`);
- the `ActionDispatcher` loop (`ActionDispatcher.fs:271`);
- `ObserverDispatcher.drain`;
- `Recurring.repeat` (`Core/Boundary.fs:96`), which drives the listener and maintenance.

F# `task` has no tail calls, so a loop that never ends should keep one pending state machine per iteration: a slow, unbounded leak in every long-running host. (`Supervisor`'s `async` loop is unaffected, because `async` trampolines `return!`.) With a store that completes synchronously (a warm SQLite file, or the recording interpreter under test), the full-batch path (`return! loop totals` when `Claimed = Batch`) also recurses on the stack, and a large backlog can raise `StackOverflowException`, which cannot be caught.
- **First, a test that should fail.** Run each loop for 100k iterations against a synchronous fake store. Assert there is no stack overflow, and that `GC.GetTotalMemory(true)` is flat (within a tolerance) between 10k and 100k iterations. It should fail on today's code; that confirms the diagnosis before anything is rewritten.
- Rewrite the four loops as `while` loops over `mutable` state. `renewWhile.renew` and `awaitSettled` are bounded by one command's lifetime, but get the same rewrite for consistency.
- On the full-batch path, `do! Task.Yield()` when the poll completed synchronously (*Consuming TAP*, `YieldLoop`). A synchronous store draining a backlog then shares the thread pool fairly, and `StopAsync` is seen promptly.

### B11. TAP conventions in F#: functional core, Task shell
Sources: Microsoft's *Asynchronous programming patterns*, *TAP overview*, *Implementing TAP* and *Consuming TAP*. TAP is the recommended pattern; EAP and APM are legacy, and nothing in the repo uses APM. `IWorkNotifications.Listen` takes `onCommands`/`onActions` callbacks, but that is not EAP: there are no events and no `EventArgs`. Passing callbacks at call time is what TAP recommends for progress (`IProgress<T>`), because it avoids handlers registered after the operation starts. They stay as F# functions.

| TAP rule | F# form | Change |
|---|---|---|
| One method returns `Task`/`Task<T>`, named with an `Async` suffix; the token is named `cancellationToken` | Members that C# sees use TAP names: `SubmitAsync(submission, cancellationToken)`. F#-facing module functions stay curried and verb-named, with the token last: `Machine.send machine id envelope ct`. Two faces, one implementation. | Every store interface member gains `Async`: `SubmitAsync`, `ClaimAsync`, `RescheduleAsync`, `ExtendLeaseAsync`, `TryGetAsync`, `TryFindAsync`, `TryGetSnapshotAsync`, `HistoryAsync`, `CommitAsync`, `RejectAsync`, `DeadLetterAsync`, `TryGetResultAsync`, `CompleteAsync`, `AbandonAsync`, `BootAsync`, `ListenAsync`, `RecordAsync`, `RegisterAsync`, and the temporal and E5 interfaces. The runtime already follows this (`StartAsync`, `PollAsync`, `RunAsync`, `EventsAsync`); the store interfaces do not. Interface parameters are renamed from `ct` to `cancellationToken`. **Public, breaking, unreleased.** |
| Throw directly only for usage errors; every other failure belongs on the returned task | Three channels, never mixed. (1) **Usage error:** `nullArg` checked before the `task {}` starts (the doc's "hybrid approach"), so it reaches the caller as a thrown exception. B7 makes most other usage errors unrepresentable. (2) **Expected outcome:** `Task<Result<_, StoreError>>`, completing `RanToCompletion`. (3) **Defect:** a `Faulted` task. | Store members check nullability outside the CE (E55). The C0 suite asserts that expected outcomes never fault. |
| A token already cancelled on entry gives a `Canceled` task. Cancellation during work need not be honoured, and the task ends `Canceled` only if cancellation actually stopped the work. | `if cancellationToken.IsCancellationRequested then Task.FromCanceled<_> cancellationToken else …` | All providers. The C0 suite asserts the shape for every member (E48). |
| Return hot tasks only | Cold effects are fine internally: `Op<'S,'T>` and `unit -> Task<_>` are descriptions composed functionally and run once at the boundary. A public member never returns `Async<'T>`, a cold `Task` or an `Op`. | A convention. `Op` is already internal. |
| In library code, prefer `ConfigureAwait(false)` | F#'s equivalent is `backgroundTask {}`. When a `SynchronizationContext` or non-default scheduler is present it starts on the thread pool, so continuations never post back to a caller's UI or legacy context. | The library has 52 `task {}` sites (Runtime, Resilience, DI, Core `Boundary`), 41 `backgroundTask {}` sites and no `ConfigureAwait`. Library sites move to `backgroundTask` (E54); tests and examples keep `task`. A CI grep keeps it that way. |
| `ValueTask` only when measurements show allocation pressure | Stay on `Task`. | None. |
| Don't dispose tasks; background work that outlives a call has explicit ownership | Already true of `Machine`'s lifecycle state. | None. |

## Phase C: correctness fixes (schema edited in place)

Each fix starts with a failing test that reproduces it on today's schema.

### C0. A conformance suite every provider runs
Today SQLite and PostgreSQL each carry their own `CommandInboxTests`, `ActionQueueTests`, `FinalizeTests`, `HistoryTests` and `ProcessorIntegrationTests`, written twice and already drifting (E29 is one result). The contract each suite defends is the same algebra, so the suite makes that explicit: **every contract rule is a named equation** with the interface operations as constructors and the typed outcomes as observations.

The equation portfolio, each one a property in the suite:
- **Idempotency:** `Submit(k, r) ▸ Submit(k, r) = AlreadySubmitted` (second submission returns the original command id).
- **Key honesty:** `Submit(k, r) ▸ Submit(k, r') = Refused(KeyReused …)` once C5 lands.
- **Claim exclusivity:** two claims never return the same command, and never two commands for one entity.
- **Head-of-line order:** a committed command's successor for the same entity becomes claimable only after it.
- **Fencing conservation:** `Commit` with an expired token answers `LeaseLost` and writes nothing; the log, snapshot and epoch are unchanged.
- **Epoch atomicity:** `Commit` with the wrong expected epoch refuses and leaves no partial write.
- **Dead-letter release:** a dead-lettered command releases its entity for the next claim.
- **History visibility:** a commit appends exactly one transition, visible to `History` at its epoch.

- **New test library** `tests/ByzantineSystems.Automata.Storage.Conformance` (Expecto, not a test runner itself). It exposes `Conformance.tests : StoreUnderTest -> Test`, where:
  ```fsharp
  type StoreUnderTest =
      { Name: string
        /// A fresh, isolated store for one test, and its teardown.
        Create: TimeProvider -> Task<IMachineStore<…> * IAsyncDisposable>
        /// What the provider offers beyond the contract, so the suite skips rather than fails.
        Capabilities: Set<Capability> }   // CrossProcess, Bitemporal, Corrections
  ```
- The suite tests **only through the public interfaces**, one named property per equation above.
- Lease tests drive time through short real leases, because the clock belongs to the database in both providers. The suite takes a `Delay` from `StoreUnderTest` for that, rather than branching on the provider.
- Both SQL test projects call `Conformance.tests`. Their duplicated contract tests are deleted, and what stays in them is schema-, SQL- or file-specific (`SchemaContractTests`, `CrossProcessTests`, migrations, boot). Program-level laws that interfaces cannot see live in B0's recording-interpreter tests instead.
- The reproduction tests below go **into the suite** wherever the bug is observable through the interfaces (C2, C3 for corrupt payloads via a provider hook, C5, C6, C7's `Suffix` once E moves it to `ITransitionLog`). C1 and C4's SQL checks stay PostgreSQL-specific.

### C1. `fsm.purge_commands` wedges maintenance once a correction is old enough (E1)
The routine deletes a doomed command's transition, error and dead letters, but not its `fsm.command_correction` row. That foreign key is NO ACTION (`009_correction.sql`), so once any correction passes the retention horizon, every `run_maintenance` fails for every machine.
- Add a `corrections AS (DELETE FROM fsm.command_correction …)` sibling CTE.
- Add a schema contract test: every FK into `fsm.command` has a matching delete in `purge_commands`. The test reads `pg_constraint` and compares it against the routine's targets, so the next child table cannot reintroduce the bug.

### C2. `received_at` can disagree with `seq` (E2)
`submit_command` stamps `COALESCE(p_received_at, STATEMENT_TIMESTAMP())`, and `STATEMENT_TIMESTAMP()` is taken **before** the routine waits on the per-entity advisory lock. Two racing submissions can therefore get `seq` and `received_at` in opposite orders. The runtime uses `ReceivedAt` as `EffectiveAt` (`CommandProcessor.fs:372`), so the later command's commit calls `close_and_open` with an instant before the live belief, which raises. The retries repeat the raise until the command is dead-lettered. A caller-supplied `ReceivedAt` (`withReceivedAt`) can do the same deliberately.
- **Database-stamped:** take `CLOCK_TIMESTAMP()` *after* the lock, and clamp it with `GREATEST(…, predecessor.received_at)`, where the predecessor is the previous `seq` (one index probe on `command_unique_seq`). A system clock that steps backwards then cannot reorder an entity.
- **Caller-supplied and earlier than the predecessor:** refuse it as a typed outcome rather than store it (see C5): `SubmissionOutcome.Refused(ArrivedBeforePredecessor predecessorReceivedAt)`.
- SQLite does the same with the write session's `Now`, which is already read inside the `IMMEDIATE` transaction.
- The rule is now part of the contract (stated on `ICommandInbox.Submit`).

### C3. One undecodable row wedges a claim batch (E6)
`Claim` decodes the batch with `List.traverseResultM`. One row whose event no longer decodes fails the whole call, and every other row in the batch stays leased until expiry, is reclaimed, and fails again. The same holds for actions.
- `Claim` decodes per row. An undecodable command is dead-lettered by the store in a follow-up `run` (fenced by the token it just received), with `CommandFailure.Machine "undecodable: <type>: <message>"`. The rest of the batch is returned. An undecodable action is abandoned the same way, with a durable `action_dead_letter` row.
- If the follow-up write fails, the row is reclaimed after the lease and the store tries again. The processor's `DeliveryCount > MaxAttempts` path never sees these rows, so the store, not the processor, owns this.
- Covers SQLite (`SqliteCommandInbox.fs:391`, `SqliteActionQueue.fs:114`) and PostgreSQL.

### C4. Actions are routed by what the client says (E7)
`finalize_command` takes `p_action_queue` from the caller on every commit. A client configured with a different queue than the one it registered at boot enqueues into the wrong queue. An empty string is a magic value meaning "drop the actions": a chart that emits actions with `ActionQueue = ""` records them in the transition and silently never delivers them.
- **Database:** commit reads the queue from `machine_maintenance.action_queue`, written at boot, and stops taking it as a parameter. If a transition has actions and the machine registered no queue, the routine raises `invalid_parameter_value` with a named message.
- **F# (public):**
  ```fsharp
  type ActionDelivery =
      | Deliver of ActionQueueName
      | Discard
  ```
  `ActionQueueName` is a validated name. It is checked against pgmq's length limit as well as the regex; verify that limit in pgmq's source in the spike. This replaces `ActionQueue: string` in `MachineStoreOptions`. `Discard` registers the empty queue explicitly.
- `ActionDelivery` lives in `Storage`, not in the PostgreSQL package, because SQLite takes it too.

### C5. Idempotency-key reuse with a different request is silent (E8)
Resubmitting a key returns the original command, whatever the new request was. A correction submitted under an event's key comes back as `AlreadySubmitted` of the event: `submit_correction` says "a repeated key returns the original, whatever it was".
- Add `request_digest bytea NOT NULL` to the command table: `sha256` of the canonical request (kind, chart version, event and correction fields). Compute it **in the database**, from `p_event::text`, so that jsonb's key reordering and whitespace normalisation make equal requests digest equally. A client-side digest of client JSON would not.
- A reused key with a different digest answers `SubmissionOutcome.Refused(KeyReused existing)`. This is **public**:
  ```fsharp
  type SubmissionRefusal =
      | KeyReused of existing: CommandId
      | ArrivedBeforePredecessor of predecessor: DateTimeOffset
  type SubmissionOutcome =
      | Accepted of CommandId
      | AlreadySubmitted of CommandId
      | Refused of SubmissionRefusal
  ```
- `submit_correction` stops writing the command row twice (insert, then `UPDATE kind`, E21). It passes `kind` into a shared internal insert. Phase H's immutability trigger depends on this.

### C6. `AlreadyFinalized` does not say what was stored (E9)
A retry whose first attempt committed, but which now sends a rejection, is told `AlreadyFinalized`, and the caller cannot tell its resolution was not the one recorded. Change it to `AlreadyFinalized of stored: Epoch * status: CommandStatus` (**public**). The routine already reads `v_status`.

### C7. Smaller fixes
- **`Suffix` completeness heuristic is wrong** (E5). It assumes epoch order equals `effective_at` order, which corrections break. Replace it with a watermark that `purge_commands` maintains:
  - an `entity_purge (machine_id, entity_id, max_purged_effective_at)` table, with no nullable columns (the sentinel is `'-infinity'`);
  - `Incomplete = max_purged_effective_at >= from`. This is exact, and costs one row per purged entity.
- **A correction with an empty belief list leaves no live belief** (E16). The next ordinary commit then reads epoch 0 and collides on `(machine_id, entity_id, epoch)`.
  - `CorrectionCommit.Beliefs` becomes non-empty by type: `Beliefs: CorrectedBelief<'State> * CorrectedBelief<'State> list`.
  - `ICorrectionStore.Correct` keeps allowing an empty list, because it is an operator tool. It can no longer move the epoch the processor reads (see E2 in Phase E).
- **`Backoff` overflow** (E17): covered by B7.

## Phase D: configurable schema (default `fsm`)

PostgreSQL only. SQLite has one schema per file.

### D1. The name is a type, not a string (public)
```fsharp
[<Struct>] type SchemaName = private SchemaName of string
type SchemaNameError =
    | Empty
    | TooLong of length: int
    | InvalidCharacters
    | Reserved of name: string
module SchemaName =
    let defaults : SchemaName   // fsm
    let tryCreate : string -> Result<SchemaName, SchemaNameError>
    let value : SchemaName -> string
```
The rules, each of them an edge case:
- `^[a-z_][a-z0-9_]*$`, lower case only. An unquoted identifier folds to lower case, so `Fsm` and `fsm` would be one schema in SQL and two in F#. Rejecting upper case removes the ambiguity, and lets every template substitute the name unquoted.
- At most 49 bytes. The longest derived identifier is `<schema>_temporal` (+9), and PostgreSQL truncates identifiers to 63 bytes without an error. A truncated name could collide silently.
- Not `pg_*`, which PostgreSQL reserves for system schemas. Not `public`, `information_schema`, `pgmq` or `cron`: `db-reset` drops the schema `CASCADE`, and those belong to someone else.
- Not a reserved keyword. Ship a static list (taken from `pg_get_keywords()` where `catcode = 'R'`). The boot check re-verifies it against the live server, whose list may be newer.

The name substitutes into SQL text, so this type is the injection boundary. `Statement.load` and the migrator accept a `SchemaName`, never a `string`.

### D2. Where the name goes
- **`PostgresContext`** gains `Schema: SchemaName`. `PostgresContext.create` uses `SchemaName.defaults`, and `PostgresContext.withSchema` overrides it. Every store and `PostgresMaintenance` already receives the context.
- **Statements:** `Statement.load (schema) domain operation` substitutes the name once, when the store is built. The text and key are cached per `(schema, domain, operation)`.
  - Edge (E24): two schemas in one process double the distinct statement texts, which can thrash Npgsql auto-preparation (`MaxAutoPrepare 32`). Size `MaxAutoPrepare` as `32 × schemas in use`, or document the knob. Benchmark before choosing.
- **Migrator (public):**
  ```fsharp
  type MigrationTarget = { ConnectionString: string; Schema: SchemaName; Beliefs: BeliefModel }   // BeliefModel in E
  Migrator.migrate : ILogger -> MigrationTarget -> Result<MigrationReport, MigrationError>
  ```
- **The `Migrate` tool** takes `--schema` / `BS_AUTOMATA_SCHEMA`. The Makefile has `SCHEMA ?= fsm`.
- **DI (public):** add `PostgresStoreSettings` (connection string name, schema, belief model, listener) bound through `IOptions<_>`, with an `IValidateOptions<_>` that runs the `tryCreate` functions and `ValidateOnStart()`. A bad schema name stops the host at startup, before any connection opens. `Microsoft.Extensions.Options` goes into the provider fsproj with `VersionOverride`, as the memory rule requires.

### D3. Templating the SQL
- **Use DbUp variables, `$schema$` and `$temporal_schema$`,** with `WithVariable`. Apply the same substitution function to the `sql/` tree, so one token syntax covers both.
  - Edge (E30): DbUp treats every `$name$` as a variable, so a future named dollar-quote tag such as `$body$` breaks the migration. No script uses one today; only `$$` and positional `$1` appear. Add a test that scans every embedded script and fails on any `$identifier$` that is not a known variable.
- **Every `fsm.` becomes `$schema$.`:** about 400 sites across 7 repeatable and 10 main scripts plus the `sql/` files. Done mechanically, then reviewed.
- **Both `SET search_path` forms are templated:** `pg_catalog, $schema$` and `pg_catalog, pg_temp`. Routines keep schema-qualifying every reference whatever the path says.
- **`temporal_versioning`** already uses `tg_table_schema`, so it works unchanged in any schema.

## Phase E: core schema plus opt-in bitemporal module

### Why
Every ordinary commit today writes about **5 to 6 rows plus one per action**:
- the transition;
- the `instance_state` portion update;
- the split remainder re-inserted;
- the trigger's history copy;
- the command status, and promotion of the next head.

`instance_state` also keeps one closed valid-time row per commit forever, because no retention removes it (E3 below). Most machines only ever read the current snapshot. A plain upsert makes it **3 to 4 rows plus actions**. The timeline is worth its cost only where someone asks `AsOf`.

### E1. Layout
- **`<schema>` (core, always installed):**
  - `machine_chart_version`, `command`, `command_error` (and the G1 children), `command_correction` (the inbox records what was asked even when this store cannot process it), `transition`, `action_dead_letter`, `machine_maintenance`, `supervision_event`, `entity_purge` (C7);
  - the new `entity_state`;
  - the core routines.
- **`<schema>_temporal` (opt-in):**
  - `instance_state`, `instance_state_history`, the `temporal_versioning` trigger;
  - `split_belief`, `close_and_open`;
  - `belief_cold` and the `belief` / `current_belief` views;
  - `correct_beliefs`, `commit_correction`, `purge_belief_history`.

  It has its own DbUp journal, `<schema>_temporal.schemaversions`. A DBA can grant or drop it separately.

### E2. `entity_state`, the core snapshot
It mirrors SQLite's `fsm_entity_snapshot`, so the two SQL stores keep identical shapes:
```sql
CREATE TABLE $schema$.entity_state (
    machine_id text NOT NULL, entity_id text NOT NULL,
    state jsonb NOT NULL, status $schema$.instance_status NOT NULL,
    epoch bigint NOT NULL CHECK (epoch > 0),
    command_id bigint NOT NULL REFERENCES $schema$.command (command_id),
    chart_version integer NOT NULL,
    effective_at timestamptz NOT NULL,
    committed_at timestamptz NOT NULL DEFAULT STATEMENT_TIMESTAMP(),
    PRIMARY KEY (machine_id, entity_id));
CREATE INDEX entity_state_command_idx ON $schema$.entity_state (command_id);
```
- **It is the only authority for an entity's epoch, in both modes.** Commit reads it `FOR UPDATE`.
  - This fixes E16 structurally. A correction always rewrites `entity_state` to its own epoch, whatever its belief list says, so no operation can make the processor read a stale epoch.
- **Edge (E20): the FK conflicts with purge.** The snapshot points at the last *succeeded* command. Purge keeps only the newest command, which may be a later rejected one, so the snapshot's command is purgeable and the FK would abort the whole purge batch.
  - `purge_commands` excludes `command_id IN (SELECT command_id FROM entity_state)` (served by the index above).
  - The contract test from C1 asserts this exclusion exists.

### E3. Opting in, and keeping clients honest (E26)
- **The database records the profile:** `$schema$.store_profile (singleton boolean PRIMARY KEY CHECK (singleton), beliefs text NOT NULL CHECK (beliefs IN ('snapshot','bitemporal')))`. The migrator sets it.
  - A temporal migration flips it to `bitemporal`.
  - Going back is refused. The migrator never drops data; a manual recipe in `docs/` drops `<schema>_temporal` and resets the row.
- **The two commit paths:**
  - **Core `commit_command`** raises when the profile is `bitemporal`. A client built without the temporal store cannot advance the snapshot while bypassing the timeline. This is the routine-level backstop.
  - **`<schema>_temporal.commit_command`** calls the shared core pieces (E5) and then `close_and_open`, in one transaction.
- **Boot compares the configured store type with the profile**, and either way round a mismatch is `BootDefect.Misconfigured`. The routine guard is the backstop, and boot is the early, readable failure.
- **Enabling later on a live database:** seed `instance_state` with one open belief per `entity_state` row, from `effective_at`, with `system_time` starting at migration time. History before the opt-in is unknown, and the seed says so in a `COMMENT`. This needs a test.
- **Retention:** `RetentionPolicy.BeliefHistory` applies only in bitemporal mode. Boot warns (logs, does not refuse) when it is set on a snapshot store.
- **Edge (E3):** closed valid-time rows in `instance_state` are never purged. Leave that unchanged, and document it in `schema-evolution.md`. If it matters later, it becomes a new retention class.

### E4. Store types: opt-in at the type level (public)
```fsharp
type BeliefModel =
    | Snapshot
    | Bitemporal

type PostgresMachineStore<…>(options)              // core: inbox, reader, processor, actions, boot, notifications, ITransitionLog
type PostgresBitemporalMachineStore<…>(options)    // the core plus ITemporalReader, ICorrectionStore, IPriorState, ICorrectionCommitter
```
- `PostgresMachineStore` stops implementing the temporal interfaces. `Store.tryTemporal` then answers truthfully by type test, which is the mechanism `MachineStore.fs` already documents.
- `PostgresBitemporalMachineStore` composes the core store rather than inheriting from it, as the current store composes its parts.
- `MachineStoreOptions.forEntityId` stays; `.bitemporal` returns the options for the second type.
- `BeliefModel` describes PostgreSQL's choice only. It is not a property every store has.

### E5. Corrections: shipped in the temporal module, open to implement over the core
Today the runtime needs `ITemporalReader` (only for the state just before `T`, `Correction.fs:45`) and `IReplayStore` (`Suffix` plus `CommitCorrection`). Split that into the smallest interfaces a third party would implement (**public**):
```fsharp
/// Reading the committed log. Core tables only, so the core stores implement it.
type ITransitionLog<'EntityId, 'State, 'Event, 'Action> =
    abstract Suffix : MachineId * 'EntityId * from: DateTimeOffset * limit: int * CancellationToken
                      -> Task<Result<ReplaySuffix<…>, StoreError>>

/// What the entity was just before an instant. The temporal store answers from beliefs; an
/// application can answer from the transition log (the to_state of the last transition
/// effective before T) or from its own records.
type IPriorState<'EntityId, 'State> =
    abstract Before : MachineId * 'EntityId * at: DateTimeOffset * CancellationToken
                      -> Task<Result<Snapshot<'State> option, StoreError>>

/// Committing a correction, fenced like any commit.
type ICorrectionCommitter<'EntityId, 'State, 'Event, 'Action> =
    abstract CommitCorrection : CommandId * LeaseToken<CommandWork> * expected: Epoch
                                * CorrectionCommit<…> * CancellationToken
                                -> Task<Result<FinalizeOutcome, StoreError>>
```
- `Store.tryCorrections` returns `CorrectionCapability option`, a record holding all three. It is `Some` only when the store implements all three at the machine's exact types. `Correction.plan` and `Replay` depend on that record only.
- `IReplayStore` is removed; `ITemporalReader` stays for `ValidAt`/`AsOf`.
- **What a third party gets from core PostgreSQL:**
  - core routines that run inside the caller's own transaction:
    - `$schema$.command_standing(command_id, token)` returns the lease/fence verdict;
    - `$schema$.append_transition(…)`;
    - `$schema$.set_entity_state(…)`;
    - `$schema$.close_command(command_id, status)`, which also promotes the next head;
  - `docs/corrections.md`, which shows a custom `ICorrectionCommitter` that opens an `NpgsqlTransaction`, calls those routines, and writes its own beliefs alongside them.

  These are the same pieces the bundled temporal commit uses, so the fence logic is written once.
- **A test-only implementation over a snapshot-only model is the evidence the split needs.** A derived `IPriorState` (the `to_state` of the last transition effective before `T`) plus an `ICorrectionCommitter` built on the core routines answers `Before` from the transition log and commits corrections under its own fence. That is the proof that the three interfaces are sufficient without beliefs, so the split must be designed for it. In particular, `IPriorState.Before` must not assume a valid-time table, and `ReplaySuffix`'s `Incomplete` flag must be computable from a purge watermark alone (C7). The recording interpreter from B0 carries the same argument at the program level.
- **Refuse at submission, not at processing (E27, E28).** Today `Machine.correct` submits regardless of capability, and the processor dead-letters the command later ("this store cannot replay corrections"). SQLite's inbox stores correction commands it can never process.
  - `Machine.correct` / `previewCorrection` return `MachineRejection.CorrectionsUnsupported` (**public, new case**) when `Store.tryCorrections` is `None`.
  - The processor's dead-letter path stays, as the backstop for a store swapped under a queued correction.

### E6. Bugs fixed while moving the temporal code
- **`system_time` can go backwards or be zero-width** (E13).
  - `STATEMENT_TIMESTAMP()` is fixed for a whole top-level statement, including every function it calls. Under concurrency it can also be *earlier* than the `LOWER(system_time)` a concurrent transaction committed: for example, `Correct` blocked behind a finalize.
  - The trigger then builds `[lower, at)` with `at < lower`, and the range constructor raises.
  - Fix: `at := GREATEST(STATEMENT_TIMESTAMP(), LOWER(OLD.system_time))`. When `at = LOWER(OLD.system_time)`, the superseded belief was never observable, so it is not archived. Both cases are tested.
- **`ICorrectionStore.Correct` is unfenced** (E4). It writes beliefs with no lease and no epoch, racing the inbox.
  - It takes `expected: Epoch`, runs under the entity's advisory lock, and answers `CorrectionOutcome.Conflict of actual: Epoch` (**public, new case**) when `entity_state` moved.
  - It still never touches `entity_state`, because it is a belief-only operator tool.
- **Two clocks in the read paths** (E14).
  - `ValidAt` asks the database for `upper(system_time) = 'infinity'` instead of passing an application-side "now".
  - The `belief_cold` cutoff uses `date_trunc('day', now() AT TIME ZONE 'UTC')`, so pg_cron and the application agree whatever their session `TimeZone`.
  - Drop `belief_cold_state` and derive staleness from `max(cutoff)` in the materialised view. The pg_cron job can only `REFRESH … CONCURRENTLY`, which cannot run inside a transaction block, so it could never mark the state anyway.
- **`purge_belief_history` is unbatched and unindexed** (E15).
  - Add an index on `(machine_id, upper(system_time))`.
  - Use `ORDER BY` plus `FOR UPDATE SKIP LOCKED` inside the `LIMIT`, like `purge_commands`.

## Phase G: less JSON (formerly B1 to B7, adjusted)

SQL providers only. The rules from the previous plan hold:
- Both SQL stores keep identical table shapes.
- What stays JSON is the user payloads behind `Codec<'T>`, plus SQLite's `exited`/`entered`.

### G1. The failure envelope becomes relational (both SQL stores)
This is unchanged from the previous B1: a `command_error` header, the `failure_kind`/`replay_failure` domains, one child table per case with a fixed `kind` and a composite FK, and sentinel-filled replay fields.
- `CASE … ELSE FALSE` is required: a `CASE` with no matching arm yields NULL, and a NULL `CHECK` passes.
- `fail_command` raises unless exactly its case's parameters are present.
- C1's contract test now covers the three children too. `purge_commands` deletes them in sibling CTEs.
- Deleted: `ReplayMapping` (both providers), the JSON halves of `encodeFailure`/`readFailure`, and the string splicing (`$"""{{"domain":%s{encoded}}}"""`).
- F# side: a `Failure` encoding with an exhaustive match over `CommandFailure`. Read back through a `LEFT JOIN` on the header and the three children, decoded with a `Spelling` on `kind` (B3).

### G2. `supervision_event.reason` becomes `text NOT NULL DEFAULT ''`
`kind` and `strategy` get domains, because both also appear in F# `Spelling`s. Delete `reasonCodec`.

### G3. Typed parallel arrays for `correct_beliefs` / `commit_correction` (temporal schema)
These replace `p_beliefs jsonb`: `p_states jsonb[]`, `p_statuses text[]`, `p_valid_froms timestamptz[]`, `p_epochs bigint[]`, `p_command_ids bigint[]` and `p_chart_versions integer[]`, read with a multi-argument `unnest(…) WITH ORDINALITY`. `BeliefPayload.fs` is deleted.

Edges:
- A multi-argument `unnest` pads shorter arrays with NULLs, so the routine raises when cardinalities differ, before any write.
- **Use `cardinality()`, never `array_length(a, 1)`** (E13b). `array_length` of an empty array is NULL, and `NULL <> n` lets the length check pass.
- A NULL *element* inside an array (Npgsql sends one for an `option`) is refused with `array_position(a, NULL) IS NOT NULL`.

### G4. `claim_actions` returns typed columns
The routine projects `machine_id`, `entity_id`, `command_id`, `epoch`, `ordinal` and `action` from the pgmq message. The projected columns are nullable in the result, because the routine never raises on one message's content. A NULL becomes a per-message decode failure, which C3 now abandons durably instead of returning it forever. `readMessage` is deleted.

### G5. Drop `transition.event` (both SQL stores)
- First add a spike test asserting `transition.event = command.event` for ordinary commits and corrections on today's schema.
- Reads join `command` on its primary key.
- `EncodedDraft` loses `EventJson`.
- Phase H's immutability trigger on `command.event` is what makes this permanently safe. C5 removed the only post-insert write to `command`'s request columns.

### G6. Send the new state once
`commit_command` uses `p_to_state` for both `entity_state` and the timeline, and `p_state` is removed.

### G7. Derive `from_state` in SQL for ordinary commits
`from_state` is `entity_state.state`, read `FOR UPDATE` before the upsert.
- F# models it as `Origin = Initial of encodedState | Continuing`, derived from `expected = Epoch.initial`.
- The routine raises on `expected = 0` without an initial state, or on an initial state at a later epoch.
- SQLite: `insert_transition` uses `COALESCE((SELECT state FROM fsm_entity_snapshot …), @from_state)`. It runs before `upsert_snapshot`, and a comment must say that the order is load-bearing.
- Corrections keep an explicit `p_from_state`.

### Phase G verification
These are unchanged from the previous plan's Phase B:
- per-case failure round-trips;
- constraint rejections (a wrong field set, a second case, an unknown kind);

## Phase H: the database enforces the lifecycle (formerly C, adjusted)

Adopted as before, with these adjustments:

### H1. Lifecycle triggers (both SQL stores)
`BEFORE UPDATE OF status … WHEN (OLD.status IS DISTINCT FROM NEW.status)`. The allowed edges:
- `ready→leased`;
- `leased→ready`, for reschedule and for `reap_leases`, which the previous list missed;
- `ready|leased→succeeded|rejected|dead_letter`.

Terminal states never change again.
- Before enabling it, list every `UPDATE … SET status` in both `sql/` trees and every routine.
  - Include C3's store-side dead-lettering and E5's `close_command`.
  - Include the SQLite equivalents.
- Failure completeness: closing as `rejected` or `dead_letter` requires the G1 header **and** its child row.

### H2. Append-only and immutable facts
- `UPDATE` is rejected on `transition`, `command_error` and its children, `action_dead_letter` and `supervision_event`.
- The request columns of `command` are immutable: `event`, `kind`, `chart_version`, `idempotency_key`, `request_digest`, `received_at`, `seq`, `machine_id` and `entity_id`.
- DELETE stays, because retention is a feature.
- The role-hardening recipe goes in `docs/`, not in a migration.

### H3. Domains for repeated checked strings
Audit the remaining inline `CHECK`s. A rule used once stays a table `CHECK`.

### Considered and not adopted
Unchanged from the previous plan:
- the `temporal_tables` extension;
- `serializable` as the default isolation;
- updatable views with `INSTEAD OF` triggers as the API;
- a ledger maintained by triggers;
- `fillfactor` without a benchmark.

Added:
- **Triggers to dispatch the bitemporal write** (an `AFTER INSERT` on `transition` calling `close_and_open`). It would keep core routines oblivious to the module, but corrections would have to suppress it. An explicit temporal `commit_command` plus the profile guard (E3) states the same thing where a reader looks for it.
- **SQLite `:memory:` as an in-process store.** Pooling gives every connection its own empty database, WAL is unavailable, and it would still pay for codecs, SQL and migrations on every start. Sharing one connection would serialise reads and writes behind `WriteGate` for no durability gain. For process-local tests, B0's recording interpreter covers the program-level laws without a database at all.
- **A durable store that snapshots to a file.** That is a second, weaker SQLite, which already exists.
- **Promoting `StubStore` to a public test double.** It fakes outcomes rather than implementing semantics, so tests against it prove nothing about ordering or fencing. Fault injection stays a test-only concern.

### Phase H verification
- Every legal edge succeeds, and every illegal one raises, in both SQL stores.
- A rejection with no error row raises.
- An `UPDATE` on each fact table raises.
- Updating `command.event` raises.
- `purge_commands` still deletes.
- The full integration suites and the C0 suite pass unchanged, which proves the trigger edges match every writer.

- `<summary>` comments, with no em dashes or `--` asides in comments.
- Exhaustive matches on `Resolution`, `Param`, `Spelling` cases, `BeliefModel` and `ActionDelivery`; no wildcard arms.
- `Row` and `Read` read by name, never by ordinal.
- Every public change is listed in its phase and recorded in `docs/public-api.md`. No version bump, tag or CHANGELOG.
- Provider packages keep `VersionOverride` in their own fsproj, and nothing is added to `Directory.Packages.props`.
- A behaviour the interfaces promise is tested in the C0 suite, not in a provider's own tests. A program-level law is tested against the recording interpreter, not re-derived per provider.
- **The store algebra (B0):** store logic is written once, as a `store { }` program; a provider contributes statements, an interpreter and sessions, never its own choreography. `StatementKey` names what a program wants; SQL text is data.

## Appendix: the three .NET async patterns in F#, keeping the functional part

This is Microsoft's `Read(buffer, offset, count)` example from *Asynchronous programming patterns*, written in F# with `Task`. B11 and Phase F follow the TAP form. EAP and APM appear only so they can be recognised and wrapped at a boundary. Neither is written in new code.

**Synchronous baseline.**
```fsharp
type Reader =
    abstract Read: buffer: byte[] * offset: int * count: int -> int
```

**TAP (the recommended pattern).** One method returns a hot `Task`, and its name ends in `Async`. The functional part is three things: a pure core, cold composable descriptions, and `Result` for expected outcomes. The `Task` sits only at the edge.
```fsharp
/// Expected outcomes are data, not exceptions.
type ReadError =
    | EndOfData
    | Unavailable of exn

/// A cold, composable description of async work: nothing runs until it is given a token.
/// This is the shape of Storage's internal `Op`, reduced to its essence.
type Effect<'T, 'E> = CancellationToken -> Task<Result<'T, 'E>>

module Effect =
    let ok (value: 'T) : Effect<'T, 'E> = fun _ -> Task.FromResult(Ok value)
    let map (f: 'T -> 'U) (e: Effect<'T, 'E>) : Effect<'U, 'E> =
        fun ct -> backgroundTask { let! r = e ct in return Result.map f r }
    let bind (f: 'T -> Effect<'U, 'E>) (e: Effect<'T, 'E>) : Effect<'U, 'E> =
        fun ct -> backgroundTask {
            match! e ct with
            | Ok value -> return! f value ct
            | Error error -> return Error error }

/// Pure core: deciding what a read means, with no I/O and no Task (TAP "Workloads").
module ReadCore =
    let interpret (bytesRead: int) : Result<int, ReadError> =
        if bytesRead = 0 then Error EndOfData else Ok bytesRead

/// TAP shell for .NET callers: hot task, `Async` suffix, `cancellationToken` last.
type StreamReader(source: Stream) =
    member _.ReadAsync(buffer: byte[], offset: int, count: int, cancellationToken: CancellationToken)
        : Task<Result<int, ReadError>> =
        ArgumentNullException.ThrowIfNull buffer                 // usage error: thrown, not on the task
        if cancellationToken.IsCancellationRequested then
            Task.FromCanceled<Result<int, ReadError>> cancellationToken   // already cancelled: Canceled
        else
            backgroundTask {                                     // F#'s ConfigureAwait(false)
                try
                    let! n = source.ReadAsync(buffer.AsMemory(offset, count), cancellationToken)
                    return ReadCore.interpret n
                with
                | :? IOException as e -> return Error(Unavailable e)   // expected: a Result
            }                                                    // anything else: a defect, Faulted

/// F# face: curried, token last, composable as an Effect before anything runs.
module StreamReader =
    let read (reader: StreamReader) (buffer: byte[]) (offset: int) (count: int) : Effect<int, ReadError> =
        fun ct -> reader.ReadAsync(buffer, offset, count, ct)

// Composition stays functional, and the Task appears only when the token is supplied:
//   let header = StreamReader.read reader buf 0 16 |> Effect.map (fun n -> buf[..n - 1])
//   let! result = header cancellationToken
```

**EAP (legacy; recognise and wrap it, never write it).** An `Async`-suffixed method returning `unit`, plus an event.
```fsharp
type ReadCompletedEventArgs(bytesRead: int, error: exn, cancelled: bool, state: obj) =
    inherit AsyncCompletedEventArgs(error, cancelled, state)
    member _.BytesRead = bytesRead

type LegacyEapReader =
    abstract ReadAsync: buffer: byte[] * offset: int * count: int -> unit
    [<CLIEvent>]
    abstract ReadCompleted: IEvent<EventHandler<ReadCompletedEventArgs>, ReadCompletedEventArgs>

/// Wrapped into TAP at the boundary with a TaskCompletionSource. The handler is attached
/// *before* the call, so a completion cannot be missed.
let readTap (r: LegacyEapReader) buffer offset count : Task<Result<int, ReadError>> =
    let tcs = TaskCompletionSource<Result<int, ReadError>>(TaskCreationOptions.RunContinuationsAsynchronously)
    let rec handler =
        EventHandler<ReadCompletedEventArgs>(fun _ e ->
            r.ReadCompleted.RemoveHandler handler
            if e.Cancelled then tcs.TrySetCanceled() |> ignore
            elif isNull e.Error then tcs.TrySetResult(ReadCore.interpret e.BytesRead) |> ignore
            else tcs.TrySetResult(Error(Unavailable e.Error)) |> ignore)
    r.ReadCompleted.AddHandler handler
    r.ReadAsync(buffer, offset, count)
    tcs.Task
```
The functional replacement for EAP's events is a **function parameter supplied at call time**. That is what `IWorkNotifications.ListenAsync(machineId, onCommands, onActions, cancellationToken)` already does, and what TAP recommends for progress (`IProgress<T>`). No events or `EventArgs` types are needed.

**APM (legacy; recognise and wrap it, never write it).** A `Begin`/`End` pair over `IAsyncResult`.
```fsharp
type LegacyApmReader =
    abstract BeginRead: buffer: byte[] * offset: int * count: int * callback: AsyncCallback * state: obj -> IAsyncResult
    abstract EndRead: asyncResult: IAsyncResult -> int

/// Wrapped into TAP with the BCL's own adapter.
let readTap (r: LegacyApmReader) buffer offset count : Task<Result<int, ReadError>> =
    backgroundTask {
        let! n = Task.Factory.FromAsync((fun cb st -> r.BeginRead(buffer, offset, count, cb, st)), r.EndRead, null)
        return ReadCore.interpret n
    }
```

The rule this appendix leaves for the repo: public surfaces are TAP; the logic behind them is pure functions and cold `Effect`/`Op` values; legacy patterns are wrapped once, at a boundary, into `Task<Result<…>>`.
